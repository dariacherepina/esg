# company-service — How It Works, Inside and Out

This guide explains every part of company-service as it stands after Step 6, and gives you
hands-on exercises to see each part working (and failing) with your own eyes.

All commands are run from the repository root in **PowerShell**.

---

## Part 1 — The big picture

### Where company-service fits

```
                       ┌──────────────────────┐
   you / Postman  ───► │  company-service     │  ◄── this guide
                       │  :8081               │
                       └─────────┬────────────┘
                                 │ REST: GET /api/companies/{id}
                       ┌─────────▼────────────┐        (later steps)
                       │  esg-score-service   │ ──► RabbitMQ "score.updated"
                       │  :8082               │        │              │
                       └──────────────────────┘        ▼              ▼
                                               portfolio-service  report-service
                                               :8083              :8084
```

company-service is the **source of truth for raw data**. It stores what a company *is*
(name, sector) and what it *measured* (CO₂, water, diversity, ...). It does **not** calculate
scores — that is esg-score-service's job. Keeping that separation means each service has one
clear purpose, which is what makes the later resource measurements meaningful.

### The layers inside company-service

```
 HTTP request (JSON)
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│ api package          "speaks HTTP"                         │
│  CompanyController   URL → method, JSON ↔ Java             │
│  CompanyRequest      what clients send (validated)         │
│  CompanyResponse     what clients receive                  │
│  ApiExceptionHandler exceptions → 400 / 404 / 409          │
└──────────────┬────────────────────────────────────────────┘
               │ Java objects only — no HTTP below this line
┌──────────────▼────────────────────────────────────────────┐
│ domain package       "knows the rules"                     │
│  CompanyService      business rules, transactions          │
│  CompanyRepository   database access (generated by Spring) │
│  Company, Sector     the data model                        │
│  *Exception          named failure cases                   │
└──────────────┬────────────────────────────────────────────┘
               │ SQL (generated by Hibernate)
┌──────────────▼────────────────────────────────────────────┐
│ PostgreSQL (Docker)  company_db.companies                  │
│  schema + seed data created by Flyway                      │
└───────────────────────────────────────────────────────────┘
```

**Rule of thumb:** each layer only talks to the one directly below it. The controller never
touches the repository; the service never sees HTTP status codes. That is why you could
replace REST with, say, a message queue without touching the domain package.

## Part 2 — File-by-file tour

```
esg/
├── pom.xml                                  ① parent POM
├── docker-compose.yml                       ② local Postgres
├── docker/postgres/init/01-create-databases.sql
└── company-service/
    ├── pom.xml                              ③ child POM (dependencies)
    └── src/
        ├── main/java/com/esg/company/
        │   ├── CompanyServiceApplication.java   ④ entry point
        │   ├── domain/                          ⑤ model + rules + DB access
        │   └── api/                             ⑥ HTTP layer
        ├── main/resources/
        │   ├── application.yml                  ⑦ configuration
        │   └── db/migration/V1__, V2__          ⑧ Flyway SQL
        └── test/java/com/esg/company/           ⑨ tests
```

### ① `pom.xml` (root) — the parent

Declares *shared* settings once: Spring Boot version (3.5.6, via `spring-boot-starter-parent`),
Java 21, and the list of modules. `<packaging>pom</packaging>` means "I produce no JAR, I only
organise modules". Every service inherits from it, so all four services will always use the
same library versions.

### ② `docker-compose.yml` + init script — local database

Runs `postgres:16-alpine` as container `esg-postgres` on port 5432 with user/password
`esg`/`esg`. The init script creates `company_db` — but **only the first time** the data volume
is empty. The `healthcheck` lets Docker report when Postgres actually accepts connections.

### ③ `company-service/pom.xml` — dependencies

| Dependency                         | What it gives you                                       |
|------------------------------------|---------------------------------------------------------|
| `spring-boot-starter-web`          | Embedded Tomcat, Spring MVC, JSON (Jackson)             |
| `spring-boot-starter-data-jpa`     | Hibernate (ORM), Spring Data repositories, HikariCP pool|
| `spring-boot-starter-validation`   | `@NotNull`, `@DecimalMax`, ... and the engine to check them |
| `flyway-core` + `flyway-database-postgresql` | Runs versioned SQL migrations at startup     |
| `postgresql` (runtime)             | JDBC driver — how Java talks to Postgres                |
| `spring-boot-starter-test` (test)  | JUnit 5, Mockito, AssertJ, MockMvc                      |

No versions are written: the parent POM decides them.

### ④ `CompanyServiceApplication.java`

`@SpringBootApplication` = "scan this package and everything below it, and auto-configure
whatever the dependencies on the classpath suggest". Because `data-jpa` and the Postgres driver
are present, Spring Boot automatically builds a connection pool, Hibernate, and Flyway — you
wrote none of that wiring.

### ⑤ `domain` package

| File | Role |
|------|------|
| `Company.java` | JPA **entity**: one object = one row in `companies`. Annotations map fields to columns. Validation annotations repeat the agreed ranges. |
| `Sector.java` | Enum of the 4 allowed sectors. Stored as text (`"ENERGY"`), never as a number. |
| `CompanyRepository.java` | An **interface only**. Spring Data reads method names like `findBySectorOrderByIdAsc` and generates the SQL at startup. |
| `CompanyService.java` | The rules: names are unique, missing ids raise `CompanyNotFoundException`. Defines **transactions** (`@Transactional`). |
| `CompanyNotFoundException`, `DuplicateCompanyNameException` | Named failure cases. The domain says *what* went wrong; the api layer decides *which HTTP status* that is. |

### ⑥ `api` package

| File | Role |
|------|------|
| `CompanyController.java` | Maps `GET/POST/PUT/DELETE /api/companies...` to service methods. Converts entity ↔ DTO. No logic. |
| `CompanyRequest.java` | Record for incoming JSON. No `id`. Uses `Double`/`Integer` so a missing field becomes `null` and fails `@NotNull` instead of silently becoming `0`. |
| `CompanyResponse.java` | Record for outgoing JSON. Decouples the API format from the database structure. |
| `ApiExceptionHandler.java` | `@RestControllerAdvice`: catches exceptions from any controller and turns them into `application/problem+json` responses. |

### ⑦ `application.yml`

```yaml
server.port: 8081
spring.datasource.url: ${DB_URL:jdbc:postgresql://localhost:5432/company_db}
spring.jpa.hibernate.ddl-auto: validate
spring.jpa.open-in-view: false
```

`${DB_URL:default}` = use environment variable `DB_URL` if set, else the default. This is how
the same JAR will run locally, in Docker and in Kubernetes without changes.

Any property can also be overridden on the command line: `java -jar app.jar --server.port=9090`.

### ⑧ Flyway migrations

* `V1__create_companies_table.sql` — the table, with `CHECK` constraints mirroring the
  validation ranges and a `UNIQUE` name.
* `V2__seed_companies.sql` — 20 fictional companies, 5 per sector, 5 per rating band.

Flyway records each applied file in the table `flyway_schema_history` together with a
**checksum**. It runs each version exactly once, in order, and refuses to start if an already
applied file was modified.

### ⑨ Tests

| Test class | Type | What's real | What's fake | Speed |
|------------|------|-------------|-------------|-------|
| `CompanyServiceTest` | unit | the service | repository (Mockito `@Mock`) | ~1 s |
| `CompanyControllerTest` | web slice | controller, JSON, validation, error handler | service (`@MockitoBean`) | ~10 s |
| *(Step 7)* integration | full | everything incl. Postgres | nothing | ~20 s |

## Part 3 — What happens when you start the app

Run `java -jar company-service/target/company-service-0.0.1-SNAPSHOT.jar` and read the log
top to bottom. Each line corresponds to one stage:

| # | Log line (shortened) | What is happening |
|---|----------------------|-------------------|
| 1 | `Starting CompanyServiceApplication using Java 24...` | JVM started, `main()` runs |
| 2 | `Bootstrapping Spring Data JPA repositories` / `Found 1 JPA repository interface` | Spring found `CompanyRepository` and will generate its implementation |
| 3 | `Tomcat initialized with port 8081` | Embedded web server created (not yet accepting requests) |
| 4 | `HikariPool-1 - Start completed.` | First real connection to Postgres opened → URL/user/password are correct |
| 5 | `Flyway ... Database: jdbc:postgresql://localhost:5432/company_db` | Flyway connected |
| 6 | `Schema "public" is up to date` *or* `Successfully applied 2 migrations` | Migrations checked / applied |
| 7 | `HHH...` Hibernate lines | Hibernate builds its model; with `ddl-auto: validate` it compares entity ↔ table |
| 8 | `Tomcat started on port 8081` | Now accepting HTTP requests |
| 9 | `Started CompanyServiceApplication in X seconds` | Ready |

Order matters: **Flyway (6) runs before Hibernate validation (7)** — so the table exists by the
time Hibernate checks it. Startup time (line 9) is itself a metric you will compare across the
Docker image variants later.

## Part 4 — Following a request through the code

### A successful read: `GET /api/companies/6`

1. **Tomcat** receives the HTTP request on port 8081.
2. **Spring MVC** finds the method mapped to `GET /api/companies/{id}` →
   `CompanyController.findById(6)`.
3. Controller calls `service.findById(6L)`.
4. `CompanyService` opens a **read-only transaction** and calls `repository.findById(6L)`.
5. **Hibernate** borrows a connection from the **Hikari pool** and sends:
   ```sql
   select c1_0.id, ..., c1_0.water_consumption from companies c1_0 where c1_0.id=?
   ```
6. Postgres returns one row → Hibernate builds a `Company` object.
7. Transaction ends, connection goes back to the pool.
8. Controller converts `Company` → `CompanyResponse` → **Jackson** serialises it to JSON.
9. Response: `200 OK` + JSON body.

### A failing write: `POST` with `renewableEnergyPct: 140`

1. Jackson converts JSON → `CompanyRequest`.
2. `@Valid` triggers Bean Validation → `@DecimalMax("100")` fails.
3. Spring throws `MethodArgumentNotValidException` — **the controller method never runs**,
   the service and database are never touched.
4. `ApiExceptionHandler.handleMethodArgumentNotValid` builds the `ProblemDetail` with the
   `errors` map → `400 Bad Request`.

### Three lines of defence for data quality

| Layer | Mechanism | Catches |
|-------|-----------|---------|
| API | `@Valid CompanyRequest` | bad input over HTTP |
| Service | `existsByName` check | duplicate names (normal case) |
| Database | `CHECK` + `UNIQUE` constraints | anything that bypasses Java (manual SQL, race conditions) |

## Part 5 — Hands-on labs

Prerequisite for all labs:

```powershell
docker compose up -d
mvn -pl company-service -am package
```

Open **two terminals**: one runs the app, the other sends requests.

### Lab 1 — Explore the API

Terminal 1:
```powershell
java -jar company-service/target/company-service-0.0.1-SNAPSHOT.jar
```

Terminal 2:
```powershell
$u = "http://localhost:8081/api/companies"
Invoke-RestMethod $u | Format-Table id, name, sector, co2Emissions, transparencyScore
Invoke-RestMethod "${u}?sector=ENERGY" | Format-Table id, name
Invoke-RestMethod "$u/6"
```

Also open <http://localhost:8081/api/companies/6> in a browser.

**Look for:** results always ordered by id; enum shown as text; numbers as `40.0` (they're
`double`).

### Lab 2 — See the error responses

`curl.exe` (not `curl`!) shows the response body even for errors:

```powershell
curl.exe -s http://localhost:8081/api/companies/999
curl.exe -s "http://localhost:8081/api/companies?sector=BANANAS"
curl.exe -s -X POST http://localhost:8081/api/companies -H "Content-Type: application/json" `
  -d '{\"name\":\"\",\"sector\":\"ENERGY\",\"co2Emissions\":5000}'
```

**Look for:** the last request reports *several* fields at once in `errors` — `name` is blank,
`co2Emissions` is too high, and every missing field is `must not be null`.

### Lab 3 — Watch the SQL Hibernate generates

Stop the app (Ctrl+C) and restart it with SQL logging switched on — without editing any file:

```powershell
java -jar company-service/target/company-service-0.0.1-SNAPSHOT.jar --spring.jpa.show-sql=true
```

Call `Invoke-RestMethod "http://localhost:8081/api/companies/6"` and
`Invoke-RestMethod "http://localhost:8081/api/companies?sector=ENERGY"`. Terminal 1 shows:

```
Hibernate: select ... from companies c1_0 where c1_0.id=?
Hibernate: select ... from companies c1_0 where c1_0.sector=? order by c1_0.id
```

**Look for:** the second query was generated purely from the method name
`findBySectorOrderByIdAsc`. Now do a POST, a PUT and a DELETE from the README and compare the
statements. Notice that PUT issues a `select` then an `update` even though the service never
calls `save()` — that's Hibernate's **dirty checking** at transaction commit.

### Lab 4 — Look inside the database

```powershell
docker exec -it esg-postgres psql -U esg -d company_db
```

Inside `psql`:
```sql
\dt                                   -- list tables: companies, flyway_schema_history
\d companies                          -- columns, types, constraints
SELECT id, name, sector FROM companies ORDER BY id;
SELECT version, description, checksum, installed_on FROM flyway_schema_history;
\q
```

**Look for:** the `CHECK` constraints in `\d companies`; the checksum Flyway stored for V1/V2.

### Lab 5 — Prove the database defends itself

Still in `psql`:
```sql
INSERT INTO companies (name, sector, co2_emissions, renewable_energy_pct, water_consumption,
  board_diversity_pct, corruption_incidents, transparency_score)
VALUES ('Bypass Co', 'ENERGY', 10, 140, 10, 10, 0, 10);
```

**Result:** `violates check constraint "companies_renewable_energy_pct_check"`. Even code that
skips the API cannot store invalid data. Try a duplicate name (`'Ashgrove Cement'`) too.

### Lab 6 — Break it on purpose: database down

```powershell
docker compose stop
java -jar company-service/target/company-service-0.0.1-SNAPSHOT.jar
```

**Result:** startup fails with `Connection to localhost:5432 refused` and
`Application run failed`. The app **refuses to start** rather than running without a database —
in Kubernetes the pod would restart until Postgres is ready. Fix: `docker compose start`.

### Lab 7 — Break it on purpose: Hibernate validation

In `Company.java`, temporarily change `@Column(name = "water_consumption", ...)` to
`@Column(name = "water_usage", ...)`, rebuild, start.

**Result:** `Schema-validation: missing column [water_usage] in table [companies]`.
`ddl-auto: validate` catches the mismatch at startup instead of letting the first request fail.
**Undo the change afterwards.**

### Lab 8 — Break it on purpose: modify an applied migration

In `V2__seed_companies.sql`, change any number (e.g. Lumina's `15` → `16`), rebuild, start.

**Result:** Flyway fails with a *checksum mismatch for migration version 2*. Applied
migrations are immutable history. **Undo the change** (the checksum matches again) — in a real
project you would add `V3__...sql` instead.

### Lab 9 — Reset to the known starting state

You have now created/deleted companies, so ids have moved on. Reset everything:

```powershell
docker compose down -v      # -v deletes the data volume
docker compose up -d        # init script + empty DB
java -jar company-service/target/company-service-0.0.1-SNAPSHOT.jar   # Flyway re-seeds
```

**Look for:** `Successfully applied 2 migrations`; ids are 1–20 again, and the next POST gets
id 21. This is the procedure before every experiment run.

### Lab 10 — Run and break the tests

```powershell
mvn -pl company-service -am test                                     # all tests
mvn -pl company-service -am test "-Dtest=CompanyServiceTest" "-Dsurefire.failIfNoSpecifiedTests=false"   # one class
```

Now sabotage the code: in `CompanyService.create`, comment out the `existsByName` check.
Run the tests again.

**Result:** `createRejectsDuplicateName` fails and tells you exactly which rule broke.
That's the purpose of the tests — they pin down every rule. **Undo the change.**

### Lab 11 — Configuration via environment variables

```powershell
$env:DB_PASSWORD = "wrong"
java -jar company-service/target/company-service-0.0.1-SNAPSHOT.jar
Remove-Item Env:DB_PASSWORD
```

**Result:** `password authentication failed for user "esg"`. The JAR is unchanged — only the
environment differs. Kubernetes will use exactly this mechanism.

## Part 6 — Self-check questions

Try to answer these; each answer is somewhere above or in the code.

1. Why does `CompanyRequest` use `Double` while `Company` uses `double`?
2. Which component turns `findBySectorOrderByIdAsc` into SQL, and when?
3. Why does Flyway need to run before Hibernate's schema validation?
4. You add a company via POST, then run `docker compose down` (without `-v`) and `up`. Is it
   still there? What about after `down -v`?
5. A client sends `"sector": "Energy"` (mixed case). What happens, and which class decides?
6. Why is there no `setId()` on `Company`?
7. Where would you change the HTTP status for "duplicate name" from 409 to 400?
8. What does `@Transactional(readOnly = true)` on the class mean for `create()`?

## Glossary

| Term | Meaning |
|------|---------|
| **Spring Boot** | Framework that auto-configures a Java application based on the libraries present |
| **Bean** | An object created and managed by Spring (controller, service, repository) |
| **Dependency injection** | Spring passes a bean's dependencies into its constructor (e.g. the service gets the repository) |
| **JPA / Hibernate** | JPA is the standard for mapping Java objects to tables; Hibernate is the implementation |
| **Entity** | A class mapped to a table (`@Entity`) |
| **Spring Data** | Generates repository implementations from interface method names |
| **Transaction** | A group of DB operations that succeed or fail together |
| **Dirty checking** | Hibernate detects changed fields on loaded entities and writes them at commit |
| **HikariCP** | Connection pool — keeps DB connections open for reuse |
| **Flyway** | Applies versioned SQL scripts once each, in order, and tracks them |
| **DTO** | Data Transfer Object — a class shaped for the API, separate from the entity |
| **Bean Validation** | Annotation-based input checks (`@NotNull`, `@DecimalMax`, ...) |
| **ProblemDetail** | Spring's type for RFC 9457 error responses (`application/problem+json`) |
| **MockMvc** | Sends fake HTTP requests to controllers in tests without a real server |
| **Mockito** | Library for creating fake objects (mocks) in tests |
| **Fat JAR** | A JAR containing the app plus all its libraries, runnable with `java -jar` |
